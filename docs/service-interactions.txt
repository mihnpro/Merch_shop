MERCH STORE
Взаимодействие сервисов — как всё это работает вместе

Этот документ — связующее звено между README (где описана
архитектура) и use-cases (где описаны сценарии). Здесь нет
кода и SQL-схем, нет манифестов Kubernetes. Здесь рассказ
о том, как семь сервисов разговаривают друг с другом,
почему именно так, и что происходит, когда что-то падает.

Если вы новый разработчик в проекте — начните с этого файла.
За час вы поймёте всю кинематику системы, и потом README
с use-cases лягут уже на готовый каркас в голове.


════════════════════════════════════════════════════════════
1. ЗАЧЕМ ЭТОТ ДОКУМЕНТ
════════════════════════════════════════════════════════════

У нас микросервисы. Это значит, что бизнес-логика размазана
по нескольким сервисам, и единственный способ понять, как
работает какая-то фича — проследить цепочку вызовов между
ними.

README отвечает на вопрос «что у нас построено»: какие
сервисы, какие технологии, какие БД. Use-cases отвечают
на вопрос «что может делать пользователь»: список сценариев
с шагами.

А вот вопрос «как именно сервисы общаются между собой,
когда пользователь нажимает кнопку» — повисает в воздухе.
Его и закрывает этот документ.


════════════════════════════════════════════════════════════
2. КАРТА СЕРВИСОВ — КТО ЕСТЬ КТО
════════════════════════════════════════════════════════════

Семь сервисов плюс один инфраструктурный компонент —
хранилище файлов. Запомнить роли несложно, если думать
о них как о сотрудниках одного офиса.

API Gateway — это охранник на входе. Принимает все запросы
от браузера, проверяет JWT-токен, смотрит на роль и решает,
кого пускать. Сам ничего не хранит и логики не содержит —
просто пересылает запросы в нужный сервис. Если положить
сюда бизнес-логику, документ закончится плохо.

User Service — отдел кадров. Здесь живут учётные записи,
хешируются пароли, выдаются JWT-токены, хранится баланс
баллов и история всех транзакций по баллам. Регистрация,
вход, refresh, смена пароля — всё через него. У User-сервиса
самая ответственная задача: он единственный, кто имеет право
менять баланс пользователя.

Product Service — каталог. Знает названия товаров, описания,
цены в баллах, доступные размеры, ключ фото в S3. Не знает
ничего ни про остатки, ни про корзины. Простой и скучный
сервис, и это его главное достоинство.

Inventory Service — кладовщик. Знает только остатки по парам
(товар, размер) и резервирования под заказы. Имеет атомарный
UPDATE для уменьшения остатков — главную защиту от двойной
продажи. Слушает Kafka, чтобы автоматически резервировать
остатки при появлении нового заказа.

Cart Service — корзина пользователя. Здесь живут позиции
до момента оформления. Хранит корзины в Postgres
(долгоживущие, восстанавливаются после рестарта) и держит
JSON-снапшот в Redis с TTL 30 минут как кеш. Если Redis
падает — Cart работает напрямую с Postgres, пользователь
ничего не замечает. Автоматической очистки корзины
по времени нет: содержимое в Postgres живёт до явных
действий пользователя.

Order Service — оформление и история заказов. Самый сложный
сервис в системе: оркеструет создание заказа, ходит в Cart,
User, публикует событие в Kafka. Использует Outbox-паттерн,
чтобы гарантировать, что событие точно уйдёт в Kafka, даже
если она в этот момент лежит.

Media Service — единственная точка входа для загружаемых
фото товаров. Принимает файл от админа (gRPC streaming
или HTTP multipart), валидирует формат и размер, пишет
в MinIO через S3 SDK (PutObject) с потоковой передачей.
Браузер с MinIO напрямую не общается.

Отдельного сервиса для админских операций нет. Админские
методы (создание/редактирование товара, изменение остатков,
начисление баллов, управление пользователями, смена статуса
заказа) живут в тех же доменных сервисах, что и
пользовательские, и доступны только при наличии role=admin
в JWT. Проверку выполняет общий интерцептор в каждом
сервисе, а также Gateway на маршрутах /admin/*.

MinIO — S3-совместимое хранилище для фото товаров. Не сервис
в полном смысле, но без него никуда: туда браузер загружает
картинки напрямую, минуя сервисы.


════════════════════════════════════════════════════════════
3. ТРИ СПОСОБА ОБЩЕНИЯ
════════════════════════════════════════════════════════════

Сервисы разговаривают тремя разными способами, и каждый
выбран под свою задачу.


3.1. gRPC — синхронные вызовы
─────────────────────────────

Основной канал. Используется везде, где пользователь
ждёт ответа: добавил товар в корзину — должен получить
подтверждение, оформил заказ — должен увидеть номер.

Почему gRPC, а не REST: бинарная сериализация быстрее,
строгий контракт через protobuf не даёт ничего сломать
случайно, HTTP/2 позволяет мультиплексировать запросы
по одному соединению.

Что происходит при сбое: вызывающий сервис ловит ошибку
gRPC, решает — ретраить или возвращать пользователю.
Сетевые таймауты — 2 секунды для лёгких запросов
(GetProduct, GetBalance) и 5 секунд для тяжёлых
(CreateOrder). Идемпотентные методы (AddPoints, AdjustStock)
ретраятся автоматически с экспоненциальным backoff.


3.2. Kafka — асинхронные события
─────────────────────────────────

В MVP всего один топик — order.created. Один продюсер
(Order), один консьюмер (Inventory).

Почему так: резервирование остатков не должно блокировать
оформление заказа. Пользователь не должен ждать, пока
Inventory обновит свои таблицы. Заказ создаётся в статусе
pending, событие летит в Kafka, Inventory его подхватывает
в своём темпе и переводит заказ в confirmed.

Гарантии: at-least-once доставка. Inventory обрабатывает
события идемпотентно по order_id — если одно и то же
событие пришло дважды, второй раз ничего не произойдёт.

Что происходит при сбое Kafka: продюсер не может потерять
событие, потому что мы используем Outbox-паттерн. Order
пишет событие в таблицу outbox в той же транзакции, что
и сам заказ. Отдельная горутина читает outbox и
отправляет в Kafka. Если Kafka лежит — горутина просто
ждёт и ретраит. Заказ при этом уже создан, баллы списаны,
пользователь получил подтверждение.


3.3. Загрузка фото через Media Service
───────────────────────────────────────

Фото загружаются единым запросом от админа в Media Service,
который сам пишет их в MinIO. Никаких прямых обращений
браузера к MinIO нет — у MinIO нет публичного PUT-эндпоинта,
а NetworkPolicy запрещает остальным сервисам сетевой доступ
к MinIO на запись.

Браузер шлёт Media.UploadPhoto(filename, content_type, bytes)
через Gateway. Media Service проверяет role=admin, валидирует
content-type (image/jpeg, image/png, image/webp) и размер
(≤ 5 МБ; лимит запроса на стороне сервиса — 6 МБ с запасом),
генерирует ключ products/{uuid}.{ext} и вызывает
MinIO.PutObject со stream-передачей тела запроса. Файл
не буферизуется целиком в памяти — gRPC streaming/multipart
обрабатываются чанками.

Что происходит при сбое: если MinIO недоступен или
PutObject упал — Media Service возвращает ошибку,
никаких полупустых состояний (объект не создан, photo_key
не выдан, товар админ не создаст).


════════════════════════════════════════════════════════════
4. КАРТА ВЫЗОВОВ — КТО КОГО ЗОВЁТ
════════════════════════════════════════════════════════════

Главное правило: вызовы идут только сверху вниз и только
к листовым сервисам. Цикл вроде «A зовёт B, B зовёт A»
запрещён. Это спасает от бесконечных рекурсий и от
ситуации «не пойму, кто из нас падает первым».


4.1. Что зовёт API Gateway
──────────────────────────

Gateway — точка входа. Он не содержит логики, только
маршрутизацию по URL и проверку JWT.

→ User.Register / Login / Refresh / Logout — авторизация
→ Product.ListProducts / GetProduct — каталог
→ Cart.AddItem / GetCart / UpdateItem / RemoveItem /
  ClearCart — операции с корзиной
→ Order.CreateOrder / GetOrder / ListUserOrders —
  заказы пользователя
→ User.GetBalance — баланс
→ User.ChangePassword — смена пароля

Что Gateway НЕ делает: не зовёт Inventory напрямую, не
зовёт Admin (для админки отдельный URL и отдельный
маршрут), не зовёт никаких write-методов Product
(они доступны только из Admin).


4.2. Что зовёт Cart Service
───────────────────────────

Cart живёт между Product и Inventory.

→ Product.GetProduct — нужно узнать актуальную цену и
  название перед сохранением позиции. Если бы Cart хранил
  это сам, при изменении цены админом старые корзины
  показывали бы устаревшую сумму.

→ Inventory.CheckStock — проверка наличия выбранного
  размера. Не резервирование! Резерв происходит только
  после оформления заказа. Здесь — только проверка,
  чтобы не дать положить в корзину то, чего нет.

Если Product упал — Cart возвращает ошибку «не удалось
добавить», корзина не меняется. Если Inventory упал —
аналогично. Никакого полупустого состояния.


4.3. Что зовёт Order Service
────────────────────────────

Самая разветвлённая логика в системе.

→ Cart.GetCart — забрать актуальную корзину пользователя
→ User.GetBalance — проверить, хватает ли баллов
→ User.DeductPoints — списать баллы. Вызов идемпотентный
  по order_id: если ретрай, второй раз не спишется.
→ (запись в свою БД заказа + outbox в одной транзакции)
→ Cart.ClearCart — очистить корзину после успешного
  оформления

После транзакции — фоновая горутина (outbox-воркер):
→ Kafka.publish(order.created) — публикация события

Если что-то упало посередине: транзакция в Postgres
откатилась, баллы не списаны, корзина не очищена,
заказ не создан. Если упало после транзакции, но до
очистки корзины — заказ создан, баллы списаны, корзина
не очищена. Это терпимо: пользователь увидит свой заказ
в истории, а корзина очистится при следующей попытке
оформления (или истечёт по TTL).


4.4. Кто слушает Kafka
──────────────────────

Inventory Service — единственный консьюмер topic order.created.

При получении события:
1. Открывает транзакцию
2. Атомарно уменьшает остатки по всем позициям
3. Создаёт запись в reservations с order_id
4. Коммитит транзакцию
5. Вызывает Order.UpdateStatus(order_id, "confirmed")

Если резервировать не удалось (товар закончился):
1. Записывает order_id в свою таблицу с пометкой failed
2. Вызывает Order.UpdateStatus(order_id, "cancelled")
3. Order запускает компенсацию (см. сценарий 5.7)

Идемпотентность: перед обработкой Inventory проверяет, нет ли
уже резерва с таким order_id. Если есть — просто коммитит
оффсет в Kafka и идёт дальше.


4.5. Админские операции
───────────────────────

Отдельного admin-сервиса нет. Админские методы живут
в тех же доменных сервисах:

→ Product.CreateProduct / UpdateProduct / DeactivateProduct
  — управление каталогом
→ Inventory.AdjustStock — изменение остатков
→ User.GrantPoints — начисление баллов
→ User.ResetPassword / BlockUser / ChangeRole / ListUsers —
  управление учётками
→ Order.ListAllOrders / AdminUpdateStatus / ExportOrders /
  GetReports — операции с заказами и аналитика
→ Media.UploadPhoto — приём загружаемого фото и запись в MinIO

Все эти методы доступны только с role=admin в JWT.
Проверку выполняют:
  1) Gateway на маршрутах /admin/*;
  2) общий интерцептор pkg/auth.AdminOnly в каждом
     gRPC-сервисе — на случай прямого обращения внутри
     кластера.


════════════════════════════════════════════════════════════
5. СКВОЗНЫЕ СЦЕНАРИИ — ПОКАДРОВО
════════════════════════════════════════════════════════════


5.1. Регистрация и вход
───────────────────────

Регистрация — самый простой сценарий, потому что задействован
только один доменный сервис.

Браузер шлёт POST /register на Gateway.
Gateway видит, что это публичный эндпоинт, JWT не требуется,
маршрутизирует в User.Register.

User Service в одной транзакции:
- проверяет, что логин свободен (запрос к таблице users)
- хеширует пароль через bcrypt с cost=12
- создаёт запись в users с role=user
- создаёт запись в points_balance с 0 баллов
- генерирует access-токен (TTL 15 минут) и refresh-токен
  (TTL 30 дней)
- сохраняет refresh-токен в Redis под ключом
  refresh:{jti}, плюс добавляет в Set
  user_refresh_tokens:{user_id} — это нужно, чтобы при
  смене пароля одной операцией отозвать все токены
  пользователя

Возвращает пару токенов. Gateway проксирует ответ браузеру.
Браузер сохраняет access в памяти, refresh в httpOnly cookie.

Дальше при каждом запросе:
1. Браузер шлёт запрос с заголовком Authorization: Bearer
2. Gateway парсит JWT, проверяет подпись, достаёт user_id
   и role
3. Gateway прокидывает user_id и role в gRPC-метаданные
4. Целевой сервис читает их из контекста и использует для
   проверки прав

Никакой сервис, кроме User, не лезет в Redis за refresh.
Никакой сервис не валидирует подпись JWT — это делает
только Gateway. Остальные доверяют тому, что в контексте.


5.2. Просмотр каталога и карточки товара
────────────────────────────────────────

Каталог — простой read-only сценарий.

Браузер: GET /products?category=t-shirts → Gateway →
Product.ListProducts.

Product возвращает массив товаров с полем photo_key
(например, "products/abc123.jpg"). Сервис не отдаёт полный
URL фото — это работа клиента. Клиент знает базовый хост
MinIO из переменной окружения (передаётся при сборке
фронтенда) и собирает URL: https://minio.merch.local/
merch-products/products/abc123.jpg.

Bucket merch-products настроен на public-read. Это значит,
что фото отдаётся без авторизации, и сервисам не нужно
генерировать presigned GET URL для каждого товара. Это
сильное упрощение: фронт может кешировать фото в CDN,
браузерный кеш работает естественно.

Карточка товара — чуть интереснее. Когда пользователь
открывает страницу товара, клиент делает два параллельных
запроса:
1. Product.GetProduct(id) — за деталями
2. Inventory.CheckStock(product_id) — за остатками по
   всем размерам

Параллельность важна, потому что Product и Inventory
ничего друг о друге не знают. Объединять их в одном
запросе через какой-нибудь BFF-слой можно, но в MVP
просто кладём ответственность на клиент.


5.3. Добавление в корзину
─────────────────────────

Пользователь нажимает «В корзину». Клиент шлёт POST /cart
с product_id, size, qty.

Gateway маршрутизирует в Cart.AddItem.

Cart Service в этом методе делает три вещи подряд:
1. Inventory.CheckStock(product_id, size) — есть ли в
   наличии нужное количество? Если нет — возвращаем
   OUT_OF_STOCK, пользователь видит сообщение, корзина
   не меняется.
2. Product.GetProduct(product_id) — узнаём актуальные
   название и цену. Это важно: если админ за время сессии
   изменит цену, в корзине должна быть новая цена.
3. Сохраняем позицию: открываем транзакцию в Postgres,
   вставляем или обновляем строку в cart_items, обновляем
   carts.updated_at, коммитим транзакцию. После этого
   best-effort перезаписываем JSON-снапшот в Redis под
   ключом cart:{user_id} с TTL 30 минут.

Зачем такая двухуровневая схема (Postgres + Redis):
- Postgres — источник истины. Корзина переживает рестарт
  Redis, переживает истечение TTL, восстанавливается
  с любого устройства.
- Redis — кеш для быстрого чтения. 99% обращений к корзине
  (отображение в шапке, проверка содержимого) идут только
  в Redis, без запросов в Postgres.

Если Redis падает в момент записи — операция в Postgres
уже зафиксирована. Cart просто инкрементирует метрику
cache_write_failed и возвращает успех. При следующем
GetCart снапшот будет пересобран из Postgres.

Если Postgres падает — операция фейлится целиком,
пользователь видит ошибку, никаких частичных состояний.

Автоматической очистки корзины по времени нет. Содержимое
в Postgres сохраняется до явных действий пользователя
(оформление заказа, очистка, удаление позиций). Единственный
TTL — на кеш в Redis (30 минут): по истечении запись просто
выпадает из кеша и при следующем GetCart пересобирается
из Postgres.


5.4. Оформление заказа — главный сценарий
──────────────────────────────────────────

Самый сложный поток в системе. Здесь задействованы пять
сервисов: Gateway, Order, Cart, User, Inventory — плюс
Kafka. Поток построен как choreography saga: нет
центрального оркестратора, каждый сервис делает свою часть
и публикует событие.

Шаг 1. Браузер шлёт POST /orders с delivery_address.
Gateway маршрутизирует в Order.CreateOrder.

Шаг 2. Order вызывает Cart.GetCart(user_id). Получает
список позиций с актуальными ценами и общую сумму. Если
корзина пуста — возвращает ошибку, никаких побочных
эффектов.

Шаг 3. Order вызывает User.GetBalance(user_id). Если
баллов меньше, чем сумма корзины — возвращает
INSUFFICIENT_POINTS, ничего больше не делает.

Шаг 4. Order вызывает User.DeductPoints с тремя
параметрами: user_id, amount, order_id. Здесь критически
важна идемпотентность по order_id: User Service в таблице
points_transactions имеет уникальный индекс по (order_id,
user_id). Если ретрай — второй вызов наткнётся на
unique violation, User вернёт текущий баланс без
повторного списания.

Шаг 5. Внутри Order Service открывается транзакция
в Postgres:
- вставка в orders со статусом pending
- вставка строк в order_items
- вставка в outbox: одна строка с типом order.created
  и сериализованным payload события
- COMMIT

Это и есть суть Outbox-паттерна: событие сохраняется
в БД в той же транзакции, что и сам заказ. Если эта
транзакция откатится — события не будет. Если закоммитится
— событие гарантированно где-то лежит и рано или поздно
улетит в Kafka.

Шаг 6. Order вызывает Cart.ClearCart(user_id). Если этот
вызов падает — не страшно: заказ уже создан, баллы списаны,
пользователь увидит свой заказ в истории. Корзина либо
будет очищена при следующей попытке оформления, либо
истечёт по TTL.

Шаг 7. Order возвращает Gateway → клиенту: order_id,
статус pending. Пользователь видит экран «Заказ оформлен».

Параллельно, в фоне, работает outbox-воркер Order-сервиса.
Это отдельная горутина, которая каждые 100 мс читает
из таблицы outbox строки с sent_at IS NULL, публикует их
в Kafka, и при успехе проставляет sent_at. Если Kafka
лежит — воркер просто крутится в цикле ретраев. События
не теряются.

Шаг 8. Inventory подхватывает событие из топика
order.created. Внутри своей транзакции:
- проверяет, нет ли уже резерва с таким order_id
  (защита от повторной обработки)
- по каждой позиции делает атомарный UPDATE stock SET
  available = available - qty WHERE product_id = ? AND
  size = ? AND available >= qty
- если хотя бы один UPDATE затронул 0 строк — товар
  закончился, транзакция откатывается, Inventory вызывает
  Order.UpdateStatus(order_id, "cancelled")
- если все UPDATE прошли — вставляет запись в reservations
  с order_id, коммитит, вызывает
  Order.UpdateStatus(order_id, "confirmed")

Шаг 9. Order обновляет статус заказа в своей БД. Если
статус cancelled — запускает компенсацию (см. 5.7).
Пользователь при следующем открытии магазина увидит
актуальный статус.


5.5. Админ добавляет товар с фото
──────────────────────────────────

Сценарий, в котором задействованы три участника: браузер
админа, Media Service и MinIO. Product Service подключается
только в самом конце.

Шаг 1. Админ выбирает файл в форме создания товара.
Браузер шлёт Media.UploadPhoto с метаданными
(filename, content_type) и содержимым файла. Для gRPC
это streaming-запрос (чанки по 64 КБ), для HTTP-фасада
Gateway это multipart/form-data.

Шаг 2. Media Service проверяет JWT (role=admin) через
общий интерцептор. Затем валидирует content-type
(разрешены image/jpeg, image/png, image/webp) и размер
(≤ 5 МБ; на стороне сервиса лимит запроса 6 МБ).

Шаг 3. Media Service генерирует случайный UUID,
формирует ключ "products/{uuid}.{ext}" и вызывает
MinIO.PutObject, передавая чанки stream'ом по мере
получения. Файл не буферизуется в памяти целиком.

Шаг 4. После успешного PutObject Media возвращает
браузеру photo_key.

Шаг 5. Браузер шлёт Product.CreateProduct со всеми
полями товара (name, price, description, sizes) и
photo_key, полученным на шаге 4.

Шаг 6. Product Service проверяет JWT (role=admin) через
общий интерцептор и сохраняет товар в свою БД с
переданным photo_key.

Шаг 7. Product возвращает админу подтверждение, товар сразу
появляется в каталоге.

Что если MinIO недоступен или PutObject упал: Media Service
возвращает Internal/Unavailable, браузер показывает
"попробуйте загрузить заново". Никаких полупустых состояний —
объект в MinIO не создан, photo_key не выдан, товар
не создаётся.

Что если файл превышает лимит или не картинка: Media
возвращает INVALID_ARGUMENT, объект в MinIO не создаётся.

Что если сервис дёрнули с поддельным JWT: ничего
не получится. Каждый сервис валидирует роль на каждом
admin-методе через интерсептор. Без role=admin вызов
возвращает PERMISSION_DENIED.


5.6. Начисление баллов пользователю
────────────────────────────────────

Самый «опасный» метод в системе — потенциальный источник
злоупотреблений. Поэтому идёт по жёсткой схеме.

Шаг 1. Админ в админ-панели открывает профиль пользователя,
вводит сумму и причину. Браузер шлёт User.GrantPoints.

Шаг 2. User Service проверяет JWT (role=admin) через
общий интерцептор и валидирует:
- сумма положительная (отрицательное начисление = списание,
  это другой метод)
- если сумма > 100 000 — требуется флаг confirmed=true
  в запросе (защита от случайной опечатки)
- причина не пустая

Шаг 3. User Service в транзакции:
- INSERT в points_transactions с переданным operation_id
  (UUID, передаётся клиентом или генерируется сервисом)
- UPDATE points_balance SET points = points + amount
- COMMIT

Уникальный индекс на points_transactions.operation_id
гарантирует, что повторный вызов с тем же operation_id
наткнётся на unique violation. В этом случае User Service
читает текущий баланс и возвращает его без изменений.
Это и есть идемпотентность.

Шаг 4. User Service возвращает админу новый баланс.


5.7. Отмена заказа — компенсация
─────────────────────────────────

Отмена бывает двух видов: автоматическая (Inventory не
смог зарезервировать) и ручная (админ отменил).
Механика компенсации одна и та же.

Триггер: Order.UpdateStatus(order_id, "cancelled").

Order Service:
1. Открывает транзакцию, читает заказ, проверяет, что
   он ещё не в финальном статусе (не delivered и не уже
   cancelled).
2. Меняет статус на cancelled, коммитит.
3. После транзакции запускает компенсацию.

Компенсация — две параллельные цепочки:

A. Вернуть баллы пользователю:
   Order вызывает User.AddPoints(user_id, original_amount,
   reason="refund: order_id", operation_id=order_id+"-refund").
   Это идемпотентная операция: если Order упал и
   ретраит — повторного начисления не будет.

B. Снять резерв в Inventory:
   Order публикует событие order.cancelled в Kafka
   (через тот же Outbox-паттерн). Inventory его слушает,
   увеличивает остатки обратно на зарезервированное
   количество, удаляет запись из reservations.

   В MVP можно упростить: Order напрямую вызывает
   Inventory.ReleaseReserve(order_id) через gRPC.
   Идемпотентность — Inventory проверяет, что резерв
   ещё существует, до его снятия.

Что если что-то из компенсации упадёт: оба действия
идемпотентны, ретрай безопасен. В худшем случае мы
имеем отменённый заказ с не возвращёнными баллами или
не снятым резервом — это диагностируется по дашборду
(заказы в статусе cancelled без транзакции refund
в points_transactions) и руками довыполняется через
админку.


════════════════════════════════════════════════════════════
6. НАДЁЖНОСТЬ — ЧТО ЛОМАЕТСЯ И КАК ВЫЖИВАЕМ
════════════════════════════════════════════════════════════

Сводка всех приёмов, которые делают систему устойчивой
к сбоям.


6.1. Outbox-паттерн
───────────────────

Используется в Order Service для гарантированной доставки
событий в Kafka. Идея: событие пишется в БД в той же
транзакции, что и бизнес-данные. Отдельный воркер досылает
события в Kafka. Гарантия — at-least-once: событие может
быть доставлено повторно, но не может быть потеряно.

Почему не публиковать в Kafka напрямую: если транзакция
с заказом закоммитится, а вызов Kafka упадёт — у нас
будет заказ без события. Если сначала опубликовать
в Kafka, а потом откатить транзакцию — будет событие
без заказа. Outbox решает обе проблемы.


6.2. Идемпотентность по order_id и audit_id
────────────────────────────────────────────

Каждый метод, меняющий состояние, имеет ключ идемпотентности:
- User.DeductPoints — по order_id (уникальный индекс в
  points_transactions)
- User.AddPoints — по audit_id (уникальный индекс там же)
- Inventory.AdjustStock — по audit_id
- Inventory резервирование из Kafka — по order_id в
  reservations
- Inventory.ReleaseReserve — по order_id

Это значит, что ретраи безопасны. Сетевые сбои, таймауты,
повторная доставка из Kafka — ничего не приводит к
двойному списанию или двойному начислению.


6.3. Choreography Saga и компенсации
─────────────────────────────────────

Мы НЕ используем центральный оркестратор (вроде Camunda
или Temporal). Вместо этого каждый сервис делает свою
часть и публикует событие, на которое реагирует следующий.

Плюсы: простота, нет единой точки отказа, легко
масштабировать.
Минусы: сложнее отслеживать end-to-end статус заказа,
компенсации нужно писать руками для каждого случая.

Для MVP с одним основным потоком (создание заказа) этот
подход оптимален.


6.4. Graceful degradation Redis
────────────────────────────────

Cart Service работает по схеме «Postgres — источник истины,
Redis — кеш». Если Redis недоступен:
- запись: операция выполняется в Postgres, попытка
  обновить Redis игнорируется (best-effort), пользователь
  не видит ошибки
- чтение: при cache miss или ошибке Redis — собираем
  снапшот из Postgres

Метрика cache_write_failed и cache_miss_rate подскажут,
когда Redis действительно лежит.

Refresh-токены в User Service хранятся ТОЛЬКО в Redis,
не в Postgres. Если Redis лежит — refresh не работает,
пользователю придётся залогиниться заново. Это
приемлемо: refresh — это удобство, а не критичная функция.


6.5. Retry и таймауты gRPC
───────────────────────────

Дефолтные политики:
- Read-методы (Get*, List*): таймаут 2 секунды,
  3 ретрая с экспоненциальным backoff (100ms, 200ms,
  400ms)
- Write-методы идемпотентные (DeductPoints, AddPoints,
  AdjustStock): таймаут 5 секунд, 3 ретрая
- Write-методы НЕ идемпотентные: 0 ретраев, тайм-аут
  5 секунд, ошибка возвращается пользователю как есть

В MVP неидемпотентных write-методов нет — мы все сделали
идемпотентными.


════════════════════════════════════════════════════════════
7. ГДЕ КАКИЕ ДАННЫЕ ЖИВУТ
════════════════════════════════════════════════════════════

DB per service — каждый сервис владеет своей БД, никто
другой не имеет прямого доступа. Хочешь читать данные
другого сервиса — иди через его gRPC API.

Product → таблица products в Postgres. Поля: id, name,
description, price_points, category, sizes, photo_key,
active.

Cart → таблицы carts и cart_items в Postgres + кеш
в Redis под ключом cart:{user_id} с TTL 30 минут.

Order → таблицы orders, order_items, outbox в Postgres.
Outbox — техническая таблица для гарантированной доставки
событий.

User → таблицы users, points_balance, points_transactions
в Postgres + refresh-токены в Redis (ключи refresh:{jti}
и user_refresh_tokens:{user_id}).

Inventory → таблицы stock и reservations в Postgres.

MinIO → bucket merch-products с публичным чтением.
Здесь только бинарники фото, никаких метаданных.

Почему так строго разделено: каждый сервис может быть
масштабирован, обновлён, отдеплоен независимо. Изменение
схемы users в User Service не ломает Product Service,
потому что Product не знает про users ничего, кроме
user_id в JWT-контексте. Это даёт нам право катить
сервисы поодиночке без координации.

Кто к чьим данным НЕ может обращаться напрямую:
- никто, кроме User, не имеет SQL-доступа к points_balance
- никто, кроме Inventory, не имеет SQL-доступа к stock

Если завтра захотим, например, посмотреть аналитику
по баллам — заводим отдельный ETL, который собирает
данные через gRPC, а не подключается напрямую к БД
User-сервиса.


════════════════════════════════════════════════════════════
8. БЕЗОПАСНОСТЬ ВЗАИМОДЕЙСТВИЙ
════════════════════════════════════════════════════════════

Три уровня защиты: JWT, NetworkPolicy, проверка ролей
в каждом доменном сервисе.


8.1. JWT и роли
───────────────

JWT выдаёт User Service. Подписан симметричным ключом
HS256 (или асимметричным RS256 для прод). Содержит
user_id, role (user или admin), exp.

Проверяет подпись только Gateway. Доменные сервисы
доверяют тому, что Gateway положил в gRPC-метаданные.
Это сильно упрощает реализацию — иначе пришлось бы
раздавать публичный ключ по всем сервисам.

Access-токен живёт 15 минут — это компромисс между
удобством (не слишком часто рефрешить) и безопасностью
(скомпрометированный токен быстро истечёт). Refresh-токен
живёт 30 дней, лежит в Redis, при смене пароля все
refresh-токены пользователя удаляются одной операцией
(SREM по user_refresh_tokens:{user_id}).


8.2. NetworkPolicy в Kubernetes
────────────────────────────────

Сетевая изоляция: даже если кто-то получит RCE в одном
сервисе, он не сможет ходить куда попало.

Правила:
- Gateway принимает входящий трафик из интернета и
  обращается к доменным сервисам только из своего
  pod-namespace.
- Каждый доменный сервис принимает gRPC-соединения только
  от Gateway и от других сервисов, которым это нужно
  по контракту (Order → User, Order → Cart, Cart →
  Product/Inventory, Inventory → Order).
- Резервирование Inventory (через Kafka) — только из
  Kafka-брокеров.

В MVP это реализуется обычными NetworkPolicy.
В перспективе можно перейти на service mesh (Istio,
Linkerd) с mTLS для аутентификации сервисов друг другу.


8.3. Защита админских методов в глубину

Защита админских методов реализована в двух слоях:

1. Gateway отклоняет любые запросы на маршруты /admin/*
   без JWT с role=admin.
2. Каждый доменный gRPC-сервис дополнительно проверяет
   роль через общий интерсептор pkg/auth.AdminOnly. Это
   защищает от прямых обращений внутри кластера, если
   Gateway будет неправильно сконфигурирован.

То есть для злоупотребления нужно получить валидный JWT
с role=admin, который выдаётся только после успешного
логина админа (хешированный bcrypt-паролем + рейт-лимитер
на Gateway).
