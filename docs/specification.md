# Спецификация — Merch Store MVP

| | |
|---|---|
| **Версия** | 1.0.0 |
| **Тип** | Внутренний корпоративный магазин мерча |
| **Стек** | Go · gRPC · Kafka · Kubernetes · PostgreSQL · Redis · MinIO |

---

## 1. Цель проекта

Предоставить сотрудникам удобный способ потратить корпоративные баллы на мерч, а компании — избавиться от ручной обработки таких запросов.

Без магазина процесс выглядит примерно так: сотрудник пишет HR, ждёт ответа, уточняет наличие, договаривается о выдаче. HR при этом тратит время на рутину вместо своей основной работы. Мерч на складе плохо учитывается, размеры заканчиваются, никто не понимает, что популярно.

Магазин решает это: сотрудник заходит, видит каталог и свой баланс, оформляет заказ за минуту, HR получает готовый список заказов на отгрузку.

---

## 2. Скоуп MVP

### Входит в MVP

- Каталог товаров с фильтрами по категориям и размерам, с фото
- Корзина с постоянным хранением (без авто-очистки по времени)
- Оформление заказа с проверкой остатков и баланса баллов
- Резервирование остатков — защита от двойной продажи
- Регистрация и вход через логин и пароль; JWT с ролями `user` и `admin`
- Просмотр истории своих заказов и баланса баллов
- Административная панель: управление каталогом и остатками, загрузка фото, начисление баллов, просмотр всех заказов и их экспорт, управление пользователями

### Не входит в MVP

- Уведомления (email, мессенджеры) — статус заказа виден в личном кабинете
- Возвраты и сложная история транзакций
- Промокоды, скидки, акции
- Автоматический фулфилмент

## 3. Пользователи и роли

В системе два типа пользователей. Роль фиксируется в JWT-токене и проверяется каждым сервисом.

### Сотрудник (role: user)

- Регистрация и вход в систему
- Просмотр каталога товаров, поиск и фильтрация
- Управление корзиной: добавление, изменение количества, удаление
- Оформление заказа
- Просмотр своих заказов и их статусов
- Просмотр баланса баллов и истории транзакций
- Смена пароля

**Не может:** видеть чужие заказы и балансы, изменять каталог, начислять себе баллы.

### Администратор (role: admin)

Всё, что может сотрудник, плюс:

- Управление каталогом: создание, редактирование, деактивация товаров
- Загрузка фото товаров в S3
- Управление остатками: изменение количества по дельте с указанием причины
- Начисление баллов любому пользователю
- Управление пользователями: сброс пароля, блокировка, изменение роли
- Просмотр всех заказов в системе с фильтрами
- Смена статуса заказа (в том числе отмена с возвратом баллов)
- Экспорт заказов в Excel
- Просмотр базовой аналитики: топ товаров, объём списанных баллов, средний чек

## 4. Функциональные требования

### 4.1 Авторизация

- Регистрация по логину, паролю и имени. Логин должен быть уникальным
- Вход по логину и паролю; система возвращает пару токенов: access (TTL 15 мин) и refresh (TTL 30 дней)
- Автоматическое обновление access-токена по refresh-токену без участия пользователя
- Выход из системы с отзывом refresh-токена
- Смена пароля отзывает все активные сессии на других устройствах
- Первый администратор создаётся через init-команду при запуске системы

### 4.2 Каталог товаров

- Список товаров с пагинацией (24 товара на страницу), сортировка по новизне
- Фильтрация по категории и поиск по названию
- Карточка товара: фото, название, описание, цена в баллах, выбор размера с индикатором наличия
- Деактивированные товары не отображаются в каталоге; позиции в уже созданных заказах сохраняются

### 4.3 Корзина

- Добавление товара в корзину с проверкой наличия нужного размера
- При добавлении фиксируются текущие цена и название (изменение каталога не влияет на уже добавленные позиции)
- Изменение количества с повторной проверкой остатков при увеличении
- Удаление позиции; полная очистка корзины
- Корзина хранится надёжно в PostgreSQL; Redis используется как кеш для быстрого чтения. При недоступности Redis корзина читается напрямую из базы (graceful degradation)
- Содержимое корзины в PostgreSQL **не очищается автоматически по времени** — оно живёт, пока сотрудник сам его не очистит или не оформит заказ. Запись в Redis имеет TTL 30 минут и подгружается из PostgreSQL при следующем обращении

### 4.4 Оформление заказа

Пошаговая оркестрация внутри Order Service:

1. Получить корзину из Cart Service
2. Проверить баланс пользователя в User Service
3. Списать баллы (идемпотентно по `order_id` — повторный вызов не приводит к двойному списанию)
4. Сохранить заказ в базе со статусом `pending`
5. Опубликовать событие `order.created` в Kafka (через Outbox-паттерн — событие сохраняется в той же транзакции с заказом)
6. Очистить корзину

После получения события Inventory Service резервирует остатки и переводит заказ в статус `confirmed`. Если зарезервировать не удалось — заказ переходит в `cancelled`, баллы возвращаются.

**Граничные случаи:**
- Недостаточно баллов → ошибка `INSUFFICIENT_POINTS`, корзина не очищается
- Kafka недоступна → Outbox-воркер дошлёт событие позже, заказ создаётся успешно
- Товар закончился за время оформления → заказ отменяется асинхронно, баллы возвращаются

### 4.5 Управление заказами (admin)

Жизненный цикл заказа: `pending` → `confirmed` → `ready_to_pickup` → `delivered`

Администратор может перевести заказ в любой следующий статус или отменить (`cancelled`). При отмене:
- Баллы возвращаются пользователю через User Service
- Резерв остатков снимается через Inventory Service

Логически некорректные переходы (например, из `delivered` в `pending`) отклоняются.

### 4.6 Загрузка фото

Файл проходит через Media Service, который сам пишет его в MinIO. Браузер в MinIO напрямую не обращается:

1. Браузер шлёт `Media.UploadPhoto(filename, content_type, bytes)` (gRPC streaming или HTTP multipart) на Gateway
2. Media Service проверяет `role=admin`, валидирует content-type (jpeg / png / webp) и размер (≤ 5 МБ)
3. Media Service генерирует ключ `products/{uuid}.{ext}` и вызывает `MinIO.PutObject` со стримом
4. Media Service возвращает браузеру `photo_key`
5. Браузер передаёт `photo_key` при создании или обновлении товара

## 5. Архитектура системы

### 5.1 Принципы

- **Микросервисная архитектура** — 7 независимых сервисов, каждый со своей базой данных
- **gRPC** — протокол для всех межсервисных вызовов; бинарная сериализация, строгий контракт
- **Единый API Gateway** — единственная точка входа; проверяет JWT, маршрутизирует запросы; маршруты `/admin/*` доступны только при `role=admin`
- **Role-based access** — роль в JWT, проверяется в каждом сервисе через общий интерцептор
- **Kafka** — асинхронная доставка одного события (`order.created`) с гарантией at-least-once через Outbox
- **S3 (MinIO)** — бинарные файлы вне основных баз данных; загрузка идёт через Media Service (браузер в MinIO напрямую не пишет)

### 5.2 Сервисы

| # | Сервис | Ответственность | Хранилище |
|---|---|---|---|
| 1 | **API Gateway** | Приём запросов, JWT-валидация, маршрутизация по роли | — |
| 2 | **Product Service** | Каталог; admin: создание, редактирование, деактивация товаров | PostgreSQL |
| 3 | **Cart Service** | Корзина пользователя | PostgreSQL + Redis (cache) |
| 4 | **Order Service** | Заказы, оркестрация покупки; admin: просмотр, экспорт, смена статуса | PostgreSQL |
| 5 | **User Service** | Профиль, аутентификация, баланс баллов; admin: начисление баллов, управление пользователями | PostgreSQL |
| 6 | **Inventory Service** | Остатки, резервирование; admin: изменение остатков | PostgreSQL |
| 7 | **Media Service** | Приём загружаемых фото от админа (multipart/streaming), валидация формата и размера, запись в MinIO | — (MinIO SDK) |

Плюс инфраструктурные компоненты: **MinIO** (S3), **Kafka**, **Redis**.

### 5.3 Межсервисные зависимости

| Источник | Цель | Когда |
|---|---|---|
| Cart | Product | Получить актуальную цену и название при AddItem |
| Cart | Inventory | Проверить наличие нужного размера при AddItem |
| Order | Cart | Получить корзину и очистить её при оформлении |
| Order | User | Проверить и списать баланс баллов |
| Order | Kafka | Опубликовать `order.created` |
| Inventory | Kafka | Получить `order.created` и зарезервировать остатки |
| Media | MinIO | Записать загруженный файл (PutObject) |

## 6. Данные

### Что хранит каждый сервис

**Product Service** — таблица товаров: название, описание, цена в баллах, категория, размеры, ключ фото в S3, флаг активности.

**Cart Service** — корзины и позиции корзин: товар, размер, количество, снапшот цены и названия на момент добавления. Параллельно кешируется JSON-снапшот всей корзины в Redis (TTL 30 мин).

**Order Service** — заказы и их позиции: пользователь, адрес, статус, итоговая сумма, детали товаров. Таблица `outbox` для надёжной публикации событий в Kafka.

**User Service** — пользователи: логин, хеш пароля (bcrypt cost=12), роль, статус. Баланс баллов в отдельной таблице. История транзакций по баллам. Refresh-токены в Redis с TTL 30 дней.

**Inventory Service** — остатки по товарам и размерам. Резервирования по заказам.

### Токены

- `access_token` — TTL 15 минут, содержит `user_id` и `role`, подписан HS256/RS256
- `refresh_token` — TTL 30 дней, хранится в Redis; при смене пароля в[text](../../Downloads/TemplateProposal.md) [text](../../Downloads/TemplateDescription.md) [text](../../Downloads/Flow.md)се токены пользователя отзываются

## 7. Надёжность и граничные случаи

| Ситуация | Поведение |
|---|---|
| Товар закончился в момент добавления в корзину | `OUT_OF_STOCK`, корзина не изменяется |
| Недостаточно баллов при оформлении | `INSUFFICIENT_POINTS`, корзина не очищается |
| Kafka недоступна | Outbox-воркер повторит публикацию позже; заказ создаётся немедленно |
| Inventory не смог зарезервировать остатки | Заказ → `cancelled`; баллы возвращаются через AddPoints |
| Redis недоступен (корзина) | Чтение и запись идут напрямую в PostgreSQL; ошибки пользователю нет |
| Повторный вызов DeductPoints (retry) | Идемпотентно по `order_id` — двойного списания не происходит |

## 8. Инфраструктура и деплой

- **Контейнеризация** — Docker (multi-stage build, distroless образы)
- **Оркестрация** — Kubernetes; неймспейс `merch-prod`
- **Kafka** — Strimzi operator; топик `order.created`: 3 партиции, replication factor 2, retention 7 дней
- **MinIO** — StatefulSet с постоянным томом 10 Gi; bucket `merch-products` с публичным чтением
- **Масштабирование** — HPA на все прикладные сервисы; gateway и order-service до 8 реплик
- **Сеть** — NetworkPolicy: доменные сервисы принимают трафик только от Gateway и между собой

### Ресурсы (базовый деплой)

| Сервис | Replicas | HPA max |
|---|---|---|
| api-gateway | 2 | 8 |
| product-service | 2 | 6 |
| cart-service | 2 | 6 |
| order-service | 2 | 8 |
| user-service | 2 | 4 |
| inventory-service | 2 | 6 |
| media-service | 1 | — |

## 9. Наблюдаемость

**Технические метрики** (Prometheus + Grafana):
- gRPC: количество запросов, latency, коды ответов — по сервису и методу
- Kafka: consumer lag по топику и партиции
- S3: количество сгенерированных upload URL

**Бизнес-метрики:**
- Количество созданных заказов
- Объём начисленных баллов
- Количество созданных товаров

**Трассировка** — OpenTelemetry + Jaeger.

**Логирование** — структурированные JSON-логи, агрегация в Loki.

## 10. Ограничения и решения (ADR)

| # | Решение | Обоснование |
|---|---|---|
| 1 | gRPC + Protobuf для синхронных вызовов | Строгий контракт, бинарная сериализация, HTTP/2 multiplexing |
| 2 | Kafka только для `order.created` | Асинхронное резервирование остатков; replay при сбое; минимум топиков в MVP |
| 3 | DB per service | Независимость сервисов, изолированные отказы, независимые миграции |
| 4 | PostgreSQL + Redis cache для корзины | PostgreSQL — источник истины (нет потерь при сбое Redis); Redis — O(1) на чтении горячих данных |
| 5 | Роль admin в JWT, проверка в каждом сервисе | Меньше сервисов, проще деплой; интерцептор переиспользуется |
| 6 | Outbox-паттерн для Kafka | Гарантия at-least-once: событие сохраняется в транзакции с заказом, воркер досылает |
| 7 | Загрузка фото через Media Service (multipart/streaming) | Браузер не общается с MinIO напрямую; единая точка валидации формата, размера и роли; ключи именования объектов контролируются сервисом |
| 8 | MinIO (S3-совместимое) | Разворачивается локально одной командой; при переезде в AWS S3 / Yandex Cloud код не меняется |
