MERCH STORE
Use Cases — сценарии использования системы

Документ описывает все возможные сценарии работы с системой
для двух типов пользователей: обычного пользователя и админа.
Система полностью обособлена, никаких интеграций с внешними
сервисами не предусмотрено.


────────────────────────────────────────────────────────────
ОБОЗНАЧЕНИЯ
────────────────────────────────────────────────────────────

Каждый use case описан по структуре:
- кто инициирует
- что должно быть выполнено заранее (предусловия)
- основной сценарий: пошаговое описание
- альтернативные сценарии: что если что-то пошло не так
- что меняется в системе после выполнения

────────────────────────────────────────────────────────────
UC-01. РЕГИСТРАЦИЯ
────────────────────────────────────────────────────────────

Инициатор: новый пользователь

Предусловия:
- пользователь открыл магазин
- учётной записи с таким логином ещё нет

Основной сценарий:
1. Пользователь на странице входа нажимает «Регистрация»
2. Открывается форма регистрации
3. Пользователь заполняет поля: логин (уникальный),
   пароль, подтверждение пароля, имя
4. Нажимает «Зарегистрироваться»
5. User-service проверяет, что логин свободен
6. User-service хэширует пароль (bcrypt)
7. User-service создаёт запись в таблице users
8. User-service создаёт запись в points_balance с
   начальным значением 0 баллов
9. User-service генерирует пару JWT-токенов (access + refresh)
10. Пользователь автоматически авторизуется и попадает в
    каталог

Альтернативные сценарии:
- Логин занят — система показывает «Такой логин уже занят»
- Пароль не соответствует требованиям (длина, символы) —
  валидация на клиенте и на сервере, ошибка с описанием
- Пароль и подтверждение не совпадают — валидация на
  клиенте
- Все поля валидны, но user-service недоступен — пользователь
  видит ошибку «Сервис временно недоступен»

Результат:
- создана запись в users
- создана запись в points_balance с 0 баллов
- пользователь авторизован, выдан JWT


────────────────────────────────────────────────────────────
UC-02. ВХОД В СИСТЕМУ
────────────────────────────────────────────────────────────

Инициатор: пользователь с существующей учётной записью

Предусловия:
- пользователь зарегистрирован

Основной сценарий:
1. Пользователь на странице входа вводит логин и пароль
2. Нажимает «Войти»
3. User-service находит пользователя по логину
4. User-service проверяет хэш пароля
5. User-service генерирует access-токен (TTL 15 минут)
   и refresh-токен (TTL 30 дней)
6. JWT-токены возвращаются клиенту
7. Клиент сохраняет токены (refresh в httpOnly cookie,
   access в памяти)
8. Пользователь попадает в каталог

Альтернативные сценарии:
- Неверный логин — система отвечает «Неверный логин или
  пароль» (общее сообщение, чтобы не давать подсказку
  потенциальному злоумышленнику)
- Неверный пароль — аналогично «Неверный логин или пароль»
- Слишком много неудачных попыток за короткое время —
  rate-limiter на gateway блокирует учётку на 5 минут

Результат:
- пользователь авторизован
- активная пара токенов


────────────────────────────────────────────────────────────
UC-03. ОБНОВЛЕНИЕ ТОКЕНА
────────────────────────────────────────────────────────────

Инициатор: клиентское приложение (автоматически)

Предусловия:
- access-токен истёк
- refresh-токен ещё валиден

Основной сценарий:
1. Клиент при любом запросе получает 401 Unauthorized
2. Клиент автоматически отправляет refresh-токен в
   user-service.Refresh
3. User-service проверяет refresh-токен
4. Если валиден — выдаёт новую пару токенов
5. Клиент повторяет оригинальный запрос с новым
   access-токеном

Альтернативные сценарии:
- Refresh-токен тоже истёк — пользователю показывается
  страница входа, нужно войти заново
- Refresh-токен отозван (например, после смены пароля) —
  система возвращает 401, пользователь логинится заново

Результат:
- выдана новая пара токенов
- пользователь продолжает работу без перерыва

UC-04. ВЫХОД ИЗ СИСТЕМЫ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован

Основной сценарий:
1. Пользователь нажимает «Выйти» в меню
2. Клиент отправляет user-service.Logout с refresh-токеном
3. User-service добавляет refresh-токен в список
   отозванных (revoked_tokens с TTL до истечения)
4. Клиент удаляет access и refresh токены из хранилища
5. Пользователь оказывается на странице входа

Результат:
- сессия завершена
- токены отозваны

UC-05. ПРОСМОТР КАТАЛОГА ТОВАРОВ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован

Основной сценарий:
1. Пользователь попадает на главную страницу магазина
2. Система запрашивает у product-service список товаров,
   отсортированный по новизне
3. Пользователь видит сетку карточек товаров: фото,
   название, цена в баллах
4. По каждой карточке отображается индикатор наличия
5. Пользователь может прокручивать страницу, при достижении
   конца догружаются следующие товары (пагинация по 24)

Альтернативные сценарии:
- Пользователь применяет фильтр по категории — система
  делает повторный запрос с параметром category
- Пользователь вводит поисковый запрос — система выполняет
  поиск по названию через product-service
- Каталог пустой — пользователь видит сообщение «Скоро
  появятся новые товары»
- Ошибка загрузки — пользователь видит сообщение об ошибке
  и кнопку «Повторить»

Результат:
- пользователь видит каталог
- никаких изменений в системе не происходит


────────────────────────────────────────────────────────────
UC-06. ПРОСМОТР КАРТОЧКИ ТОВАРА
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован
- товар существует и активен

Основной сценарий:
1. Пользователь кликает на карточку товара в каталоге
2. Открывается страница товара
3. Система запрашивает детали через product-service.GetProduct
4. Параллельно запрашивает остатки по всем размерам через
   inventory-service.CheckStock
5. Пользователь видит: большое фото, название, развёрнутое
   описание, цену в баллах, селектор размеров
6. Размеры, которых нет в наличии, показываются как
   неактивные с пометкой «нет в наличии»
7. Пользователь может выбрать размер и количество (по
   умолчанию 1)
8. Кнопка «В корзину» становится активной только после
   выбора доступного размера

Альтернативные сценарии:
- Товар деактивирован админом, пока пользователь смотрел
  ссылку — система показывает сообщение «Товар недоступен»
- Товар полностью отсутствует — кнопка «В корзину»
  заблокирована, отображается «Нет в наличии»
- Фото не загрузилось из S3 — показывается заглушка

Результат:
- пользователь изучил детали товара
- ничего в системе не меняется


────────────────────────────────────────────────────────────
UC-07. ДОБАВЛЕНИЕ ТОВАРА В КОРЗИНУ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован
- товар активен и доступен в выбранном размере

Основной сценарий:
1. Пользователь на странице товара выбирает размер и
   количество
2. Нажимает «В корзину»
3. Cart-service получает запрос AddItem
4. Cart-service вызывает inventory-service.CheckStock
   для проверки наличия выбранного размера
5. Cart-service вызывает product-service.GetProduct для
   получения актуальной цены и названия
6. Cart-service в транзакции записывает позицию в Postgres
   (таблицы carts и cart_items, обновляет carts.updated_at),
   затем перезаписывает JSON-снапшот в Redis под ключом
   cart:{user_id} с TTL 30 минут
7. Пользователь видит подтверждение «Добавлено в корзину»
   и обновлённый счётчик корзины в шапке

Альтернативные сценарии:
- Товар закончился между просмотром и добавлением — система
  возвращает ошибку OUT_OF_STOCK, показывает сообщение
  «К сожалению, этот размер только что закончился»
- Запрошенное количество больше доступного — система
  показывает «В наличии только N штук»
- Товар уже есть в корзине — система увеличивает количество,
  если итоговое значение не превышает остатков
- Redis недоступен — операция выполняется напрямую в Postgres,
  пользователь не видит ошибки; в метрику cache_write_failed
  пишется инкремент (graceful degradation)
- Postgres недоступен — система показывает ошибку «Не удалось
  добавить, попробуйте позже», состояние корзины не меняется

Результат:
- товар добавлен в корзину пользователя (Postgres)
- Redis-снапшот cart:{user_id} обновлён (если кеш доступен)
- автоматической очистки корзины по времени нет: содержимое
  в Postgres сохраняется до явных действий пользователя
  (оформление заказа, очистка, удаление позиций); TTL 30 мин
  применяется только к кешу в Redis

UC-08. ПРОСМОТР КОРЗИНЫ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован

Основной сценарий:
1. Пользователь нажимает на иконку корзины в шапке
2. Открывается страница корзины
3. Cart-service пытается прочитать JSON-снапшот из Redis;
   при cache miss или недоступности Redis собирает корзину
   из Postgres (carts + cart_items) и best-effort
   перезаписывает Redis с TTL 30 минут
4. Пользователь видит список позиций: фото, название, размер,
   количество, цена за единицу, сумма по позиции
5. Внизу отображается итоговая сумма в баллах
6. Рядом с итоговой суммой показывается текущий баланс
   пользователя и разница (хватает / не хватает)
7. Видны кнопки «Перейти к оформлению» и «Очистить корзину»

Альтернативные сценарии:
- Корзина пуста — отображается сообщение «Ваша корзина
  пуста» и кнопка «Перейти в каталог»
- Redis-кеш истёк по TTL — снапшот прозрачно пересобирается
  из Postgres, пользователь видит корзину без задержки
- Один из товаров был деактивирован админом — позиция
  помечается как недоступная, при оформлении такие позиции
  пропускаются с предупреждением

Результат:
- пользователь видит свою корзину
- никаких изменений в системе нет


────────────────────────────────────────────────────────────
UC-09. ИЗМЕНЕНИЕ КОЛИЧЕСТВА В КОРЗИНЕ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован
- в корзине есть товар

Основной сценарий:
1. Пользователь на странице корзины нажимает «+» или «-» у
   позиции
2. Cart-service получает запрос на обновление количества
3. Если количество увеличивается, cart-service проверяет
   остатки через inventory-service.CheckStock
4. Cart-service в транзакции обновляет cart_items в Postgres
   и carts.updated_at, затем перезаписывает Redis-снапшот
   с TTL 30 минут
5. Сумма по позиции и общая сумма пересчитываются

Альтернативные сценарии:
- Количество уменьшается до 0 — позиция удаляется из корзины
- Запрошенное количество превышает остатки — система
  показывает «В наличии только N штук», количество остаётся
  максимально доступным

Результат:
- количество товара в корзине обновлено в Postgres
- Redis-снапшот синхронизирован (если кеш доступен)


────────────────────────────────────────────────────────────
UC-10. УДАЛЕНИЕ ТОВАРА ИЗ КОРЗИНЫ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован
- в корзине есть товар для удаления

Основной сценарий:
1. Пользователь нажимает на иконку удаления у позиции в
   корзине
2. Cart-service получает запрос RemoveItem
3. Позиция удаляется из cart_items в Postgres,
   carts.updated_at обновляется
4. Cart-service синхронизирует Redis-снапшот (либо
   перезаписывает новый JSON, либо удаляет ключ, если
   корзина опустела)
5. Сумма по корзине пересчитывается
6. Пользователь видит обновлённую корзину

Альтернативные сценарии:
- Пользователь нажимает «Очистить корзину» — корзина
  полностью очищается через ClearCart
- Позиция уже была удалена в другой вкладке — операция
  идемпотентна, ошибки не возникает

Результат:
- позиция удалена из Postgres
- Redis-снапшот синхронизирован
- если корзина опустела, запись carts удалена и ключ
  cart:{user_id} в Redis тоже удалён

UC-11. ОФОРМЛЕНИЕ ЗАКАЗА
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован
- в корзине есть хотя бы одна позиция
- пользователь готов подтвердить покупку

Основной сценарий:
1. Пользователь в корзине нажимает «Перейти к оформлению»
2. Открывается страница оформления заказа
3. Пользователь видит сводку: позиции, общая сумма, баланс
4. Заполняет поле адреса доставки
5. Нажимает «Подтвердить заказ»
6. Order-service получает CreateOrder
7. Order-service вызывает cart-service.GetCart
8. Order-service вызывает user-service.GetBalance
9. Если баллов достаточно, вызывает
   user-service.DeductPoints с order_id для идемпотентности
10. Сохраняет заказ в БД со статусом pending
11. Публикует событие order.created в Kafka (через Outbox)
12. Вызывает cart-service.ClearCart
13. Возвращает пользователю номер заказа и подтверждение
14. Пользователь видит экран «Заказ оформлен» с номером
    заказа
15. В фоне: inventory-service потребляет событие из Kafka
    и резервирует остатки

Альтернативные сценарии:
- Недостаточно баллов на шаге 9 — order-service возвращает
  ошибку INSUFFICIENT_POINTS, ничего не списывается,
  корзина не очищается, пользователь видит «Не хватает
  X баллов»
- Один из товаров закончился за время оформления —
  inventory-service не сможет зарезервировать остатки,
  изменит статус заказа на cancelled через UpdateStatus,
  баллы вернутся обратно через AddPoints; пользователь
  получит уведомление в личном кабинете при следующем
  открытии
- Kafka временно недоступна — Outbox-воркер дошлёт
  событие позже, заказ создаётся успешно
- DeductPoints вызывается повторно (retry) — операция
  идемпотентна по order_id, двойного списания не происходит

Результат:
- создан заказ в order-service
- баллы списаны с баланса
- запись в points_transactions
- событие order.created в Kafka
- корзина очищена
- после резерва — заказ переходит в статус confirmed,
  записи в stock и reservations обновлены

UC-12. ПРОСМОТР ИСТОРИИ ЗАКАЗОВ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован

Основной сценарий:
1. Пользователь заходит в личный кабинет
2. Открывает раздел «Мои заказы»
3. Система через order-service.ListUserOrders запрашивает
   заказы текущего пользователя
4. Пользователь видит список заказов: номер, дата, статус,
   сумма в баллах
5. Может фильтровать по статусу: все, в обработке,
   готовы к выдаче, получены, отменены
6. Список отсортирован по дате создания (новые сверху)

Альтернативные сценарии:
- Заказов нет — отображается сообщение «У вас пока нет
  заказов» с кнопкой «Перейти в каталог»

Результат:
- пользователь видит свои заказы
- никаких изменений в системе не происходит

UC-13. ПРОСМОТР ДЕТАЛЕЙ ЗАКАЗА
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован
- заказ принадлежит этому пользователю

Основной сценарий:
1. Пользователь в списке заказов кликает на конкретный
   заказ
2. Открывается страница деталей
3. Order-service.GetOrder возвращает заказ
4. Пользователь видит: номер заказа, дату создания, текущий
   статус, список позиций (товар, размер, количество,
   цена), общую сумму, адрес доставки

Альтернативные сценарии:
- Пользователь пытается открыть чужой заказ по прямой
  ссылке — order-service проверяет user_id и возвращает
  ошибку PERMISSION_DENIED, пользователь видит 403

Результат:
- пользователь видит детали заказа
- никаких изменений в системе нет

UC-14. ПРОВЕРКА БАЛАНСА БАЛЛОВ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован

Основной сценарий:
1. Пользователь заходит на любую страницу магазина
2. В шапке отображается текущий баланс — это значение
   запрашивается у user-service.GetBalance при загрузке
3. Пользователь может зайти в раздел «Баланс» в личном
   кабинете для просмотра деталей и истории транзакций

Альтернативные сценарии:
- Пользователь новый, баланс 0 — отображается «0 баллов»
  без ошибок
- User-service временно недоступен — баланс не показывается,
  но остальной интерфейс работает

Результат:
- пользователь видит свой баланс
- система не меняется

UC-15. СМЕНА ПАРОЛЯ
────────────────────────────────────────────────────────────

Инициатор: пользователь

Предусловия:
- пользователь авторизован

Основной сценарий:
1. Пользователь заходит в раздел «Профиль»
2. Нажимает «Сменить пароль»
3. Вводит текущий пароль, новый пароль, подтверждение
4. User-service проверяет текущий пароль
5. Если верный — сохраняет новый хэш
6. Все refresh-токены пользователя помечаются как отозванные
7. Пользователь автоматически разлогинивается на других
   устройствах
8. На текущем устройстве остаётся активным

Альтернативные сценарии:
- Текущий пароль неверен — система отказывает с сообщением
- Новый пароль не соответствует требованиям — валидация

Результат:
- хэш пароля обновлён
- активные refresh-токены отозваны

────────────────────────────────────────────────────────────
UC-16. СОЗДАНИЕ ПЕРВОГО АДМИНА
────────────────────────────────────────────────────────────

Инициатор: разработчик при первом запуске системы

Предусловия:
- система развёрнута
- админов в системе ещё нет

Основной сценарий:
1. Разработчик выполняет init-команду или миграцию,
   которая создаёт первого админа с заранее заданным
   логином и паролем (из переменных окружения)
2. В таблице users появляется запись с role=admin
3. После первого входа разработчик меняет пароль

Альтернативные сценарии:
- Команда вызывается повторно — проверяется, что админ
  уже существует, повторное создание блокируется

Результат:
- в системе есть хотя бы один админ


────────────────────────────────────────────────────────────
UC-17. ВХОД АДМИНА
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- учётная запись имеет роль admin

Основной сценарий:
1. Админ открывает панель управления и вводит логин и пароль
2. User-service аутентифицирует и возвращает JWT с
   role=admin в payload токена
3. Gateway проверяет роль при каждом запросе к /admin/*
4. Если роль admin — доступ разрешён, запрос проксируется
   в нужный доменный сервис

Альтернативные сценарии:
- Пользователь без роли admin пытается зайти —
  Gateway возвращает 403 Forbidden, отображается
  ошибка «Доступ запрещён»

Результат:
- админ авторизован
- сессия активна


────────────────────────────────────────────────────────────
UC-18. ДОБАВЛЕНИЕ НОВОГО ТОВАРА
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован
- у админа есть фото товара и информация о нём

Основной сценарий:
1. Админ в панели управления нажимает «Добавить товар»
2. Открывается форма создания товара
3. Админ заполняет поля: название, описание, категория,
   цена в баллах, доступные размеры
4. Админ выбирает фото товара через файловый диалог
5. Браузер шлёт media-service.UploadPhoto с метаданными
   (filename, content_type) и содержимым файла
   (gRPC streaming или HTTP multipart) через Gateway
6. Media-service проверяет роль (role=admin), content-type
   (jpeg, png, webp) и размер (≤ 5 МБ)
7. Media-service генерирует ключ products/{uuid}.{ext},
   пишет файл в MinIO через PutObject (stream),
   возвращает photo_key
8. Админ заполнил все поля и нажимает «Сохранить»
9. Браузер вызывает Gateway → product-service.CreateProduct
   со всеми полями и photo_key
10. Product-service проверяет роль и сохраняет товар в БД
11. Товар сразу появляется в каталоге для всех пользователей

Альтернативные сценарии:
- Файл слишком большой (> 5 MB) — браузер валидирует
  размер перед отправкой; повторная проверка на стороне
  media-service возвращает INVALID_ARGUMENT
- Неподдерживаемый формат файла — media-service отказывает
  с INVALID_ARGUMENT, объект в MinIO не создаётся
- Запись в MinIO не удалась — media-service возвращает
  UNAVAILABLE/INTERNAL, photo_key не выдан, товар не создан
- product-service временно недоступен — Gateway возвращает
  ошибку, товар не создан (фото уже в MinIO; ключ может
  быть очищен фоновым cleanup-воркером, см. UC-19)
- Цена указана отрицательная — product-service возвращает
  ошибку валидации

Результат:
- фото загружено в bucket merch-products S3
- товар сохранён в product-service
- товар доступен в каталоге


────────────────────────────────────────────────────────────
UC-19. РЕДАКТИРОВАНИЕ ТОВАРА
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован
- товар существует

Основной сценарий:
1. Админ открывает список товаров в панели управления
2. Кликает на товар для редактирования
3. Открывается форма с текущими значениями
4. Админ меняет нужные поля (например, цену или описание)
5. При необходимости загружает новое фото (повторяя шаги
   с UploadPhoto из UC-18 через media-service)
6. Нажимает «Сохранить»
7. Gateway → product-service.UpdateProduct
8. Product-service проверяет роль и обновляет запись в БД
9. Изменения сразу видны в каталоге

Альтернативные сценарии:
- Админ не изменил ни одного поля — кнопка «Сохранить»
  отключена
- Параллельное редактирование двумя админами — последний
  «победил» (last-write-wins по updated_at)

Результат:
- товар обновлён в product-service
- старое фото в S3 остаётся (его можно зачистить
  отдельным cleanup-воркером по расписанию)


────────────────────────────────────────────────────────────
UC-20. ДЕАКТИВАЦИЯ ТОВАРА
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован
- товар существует и активен

Основной сценарий:
1. Админ в админ-панели выбирает товар
2. Нажимает «Деактивировать»
3. Появляется диалог подтверждения
4. Админ подтверждает
5. Gateway → product-service.DeactivateProduct
6. Product-service проверяет роль и помечает active=false
   (мягкое удаление, запись остаётся для исторических заказов)
7. Товар пропадает из каталога

Альтернативные сценарии:
- У товара есть незавершённые заказы — это не блокирует
  деактивацию, существующие заказы продолжают
  обрабатываться, новые не создаются
- Админ позже хочет вернуть товар — может вызвать
  UpdateProduct с active=true

Результат:
- товар недоступен в каталоге


────────────────────────────────────────────────────────────
UC-21. УПРАВЛЕНИЕ ОСТАТКАМИ ТОВАРА
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован
- товар существует

Основной сценарий:
1. Админ в админ-панели заходит в раздел «Остатки»
2. Видит таблицу: товар, размер, текущий остаток
3. Выбирает строку и нажимает «Изменить»
4. Указывает дельту (например, +50 при поступлении партии,
   или -3 при списании брака)
5. Указывает причину изменения
6. Gateway → inventory-service.AdjustStock (delta, reason)
7. Inventory-service проверяет роль и выполняет атомарный
   UPDATE stock SET available = available + delta
   WHERE product_id = ? AND size = ?
8. Возвращает новое значение
9. Админ видит обновлённый остаток

Альтернативные сценарии:
- Дельта отрицательная, делающая остаток отрицательным —
  inventory-service возвращает ошибку, операция не применяется

Результат:
- остаток обновлён в inventory-service


────────────────────────────────────────────────────────────
UC-22. НАЧИСЛЕНИЕ БАЛЛОВ ПОЛЬЗОВАТЕЛЮ
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован
- пользователь существует в системе

Основной сценарий:
1. Админ заходит в раздел «Пользователи»
2. Находит нужного пользователя через поиск по логину или
   имени
3. Открывает его профиль
4. Нажимает «Начислить баллы»
5. Указывает сумму и причину начисления (например, «Бонус
   за участие в проекте X»)
6. Gateway → user-service.GrantPoints(user_id, amount, reason)
7. User-service проверяет роль и в транзакции:
   - вставляет запись в points_transactions
   - увеличивает баланс в points_balance
8. Возвращает новый баланс
9. Админ видит подтверждение и обновлённый баланс
   пользователя

Альтернативные сценарии:
- Указана отрицательная сумма — user-service отказывает
  с ошибкой валидации
- Указана очень большая сумма (например, > 100000) —
  user-service требует дополнительного подтверждения
  (защита от опечатки)
- Пользователь не найден — user-service возвращает NOT_FOUND

Результат:
- баланс пользователя увеличен
- запись в points_transactions
- пользователь при следующем открытии магазина видит
  обновлённый баланс


────────────────────────────────────────────────────────────
UC-23. УПРАВЛЕНИЕ ПОЛЬЗОВАТЕЛЯМИ
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован

Основной сценарий:
1. Админ открывает раздел «Пользователи»
2. Видит список всех зарегистрированных пользователей:
   логин, имя, дата регистрации, баланс
3. Может найти пользователя через поиск
4. Может открыть профиль конкретного пользователя
5. В профиле доступны действия:
   - сбросить пароль (новый пароль показывается админу
     один раз, пользователю нужно его передать любым
     способом вне системы)
   - заблокировать учётную запись
   - изменить роль (повысить до админа или понизить)
   - посмотреть историю транзакций по баллам
   - посмотреть историю заказов

Альтернативные сценарии:
- Админ пытается заблокировать самого себя — user-service
  отказывает
- Админ пытается понизить роль последнего админа в системе —
  user-service отказывает (должен оставаться минимум один
  активный админ)

Результат:
- для соответствующих действий — изменения в user-service

UC-24. ПРОСМОТР ВСЕХ ЗАКАЗОВ

- админ авторизован

Основной сценарий:

3. Админ видит таблицу всех заказов: номер, пользователь,

UC-25. ВЫГРУЗКА ЗАКАЗОВ В EXCEL
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован

Основной сценарий:
1. Админ в разделе «Заказы» применяет фильтры (например,
   «оплаченные за последнюю неделю»)
2. Нажимает «Экспорт в Excel»
3. Gateway → order-service.ExportOrders с фильтрами
4. Order-service проверяет роль и формирует Excel-файл со столбцами:
   номер заказа, пользователь, товар, размер, количество,
   адрес доставки, дата заказа
5. Gateway возвращает файл админу
6. Браузер скачивает файл

Альтернативные сценарии:
- Фильтр возвращает 0 заказов — кнопка экспорта
  заблокирована
- Слишком большой объём данных (например, > 10000 заказов) —
  система генерирует файл асинхронно и присылает ссылку
  на скачивание

Результат:
- админ получает Excel-файл
- файл может быть использован для дальнейшей обработки


────────────────────────────────────────────────────────────
UC-26. ИЗМЕНЕНИЕ СТАТУСА ЗАКАЗА
────────────────────────────────────────────────────────────

Инициатор: админ

Предусловия:
- админ авторизован
- заказ существует

Основной сценарий:
1. Админ открывает детали заказа
2. Видит текущий статус (например, confirmed)
3. Выбирает новый статус из выпадающего списка:
   ready_to_pickup (готов к выдаче), delivered (получен),
   cancelled (отменён)
4. Если выбран cancelled, появляется поле для указания
   причины
5. Gateway → order-service.UpdateStatus
6. Order-service проверяет роль
7. Если статус cancelled — order-service дополнительно
   запускает компенсацию: AddPoints через user-service,
   ReleaseReserve через inventory-service
8. Пользователь при следующем открытии магазина видит
   новый статус

Альтернативные сценарии:
- Попытка перейти из delivered в pending —
  order-service отказывает (нелогичный переход)
- При отмене пользователь уже забрал товар — админ
  использует другой статус, отмена применяется только
  для неполученных заказов

Результат:
- статус заказа обновлён
- если cancel — баллы возвращены, резерв снят

════════════════════════════════════════════════════════════
СВОДНАЯ ТАБЛИЦА — КТО ЧТО МОЖЕТ
════════════════════════════════════════════════════════════

Пользователь:
- регистрация и вход
- смена своего пароля
- выход из системы
- просмотр каталога, поиск, фильтры
- просмотр карточек товаров
- добавление/удаление/изменение в корзине
- оформление заказа
- просмотр своих заказов и их деталей
- просмотр своего баланса и истории транзакций

Пользователь НЕ может:
- видеть чужие заказы
- видеть чужой баланс
- изменять каталог
- начислять себе баллы
- доступ к админ-панели

Админ (всё, что может пользователь, плюс):
- управление каталогом: создание, редактирование,
  деактивация товаров
- загрузка фото в S3
- управление остатками
- начисление баллов любому пользователю
- управление пользователями: сброс паролей, блокировка,
  изменение ролей
- просмотр всех заказов в системе
- изменение статусов заказов
- выгрузка заказов в Excel
- просмотр базовой аналитики

Что не может никто (не входит в MVP):
- удалять заказы из истории
- редактировать прошлые транзакции по баллам
